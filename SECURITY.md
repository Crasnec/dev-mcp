# Security policy

This service intentionally exposes arbitrary shell execution and destructive workspace operations after OAuth authorization. Treat every access token and administrator Google account as high-value credentials.

Report vulnerabilities privately to the repository owner. Do not include real access tokens, password hashes, workspace contents, or audit logs in a public issue.

The supported boundary is the current main branch. Docker daemon compromise, upstream container image or package-registry compromise, and host-kernel/container-runtime escapes are outside the application threat model.

The separate provisioner is a trusted host control-plane service with Docker daemon access and a read-only account database mount. It has no network or HTTP endpoint, polls approved accounts, validates UUID and runner identity, and invokes a fixed creation helper. The gateway and all runners have no Docker access. Pending/disabled accounts are skipped; existing stopped containers are not restarted automatically. Approval withdrawal cannot cancel a Docker creation already in flight, but account authentication checks continue to block access.

Every approved account, administrators included, receives a dedicated runner container, workspace/data storage, a bridge network, and an authenticated IPC endpoint; there is no shared runner. The gateway chooses the runner from the authenticated account; clients cannot supply a runner identity. Every IPC call is HMAC-signed with the account's own key. Runners refuse to start without a key and reject unsigned requests, so redirecting one account's socket to another runner fails authentication. No runner mounts the shared parent IPC directory.

Projects are private to their owner's execution environment. Administrators can inspect users and project metadata; administrator privileges are trusted service-wide privileges. Do not promote untrusted users.

Disabling an account or revoking its credentials prevents subsequent authenticated requests and image retrieval. It does not interrupt already-dispatched commands or stop background processes; the operator must stop the user's container to terminate them. All containers still share the host kernel, and default resource limits do not prevent a user from consuming excessive host resources. Apply host/container resource limits for untrusted workloads.

The gateway must run as a single process when using the JSON stores; the in-process write queue does not coordinate multiple gateway replicas. Back up user records together with OAuth state so credential versions are not rolled back independently.

Accounts are created only by Google OIDC sign-in and require administrator approval. No account is seeded, and there is no password login, password registration or account linking. The first administrator is approved through the local onboarding, or with the gateway stopped through the CLI bootstrap. Google identities are bound by the verified `sub`, never matched or merged by email, and cannot be reassigned through the login flow.

Google sign-in uses state, nonce and PKCE; ID tokens must have a valid RS256 signature from Google's keys, accepted issuer, correct audience/authorized party, recent issuance, unexpired lifetime and verified email. Browser and MCP credentials are issued only for active accounts. Google access/refresh tokens are not persisted. Provider errors are not reflected or logged. Authentication URLs containing codes/transactions are omitted from Caddy access logs, and form pages use `Referrer-Policy: same-origin` to preserve native form Origin headers while suppressing cross-origin referrers (non-form pages use `no-referrer`); configure any upstream proxies consistently.

Google credentials are loaded only by the gateway at runtime. `scripts/import-google-secrets.mjs` copies the named files without reading their contents into logs or command arguments; `compose.google.yaml` mounts only the two files, never the whole plan-app directory. Preserve the mode-0700 parent directory of the read-only copies. Keep originals, copies and backups out of repositories/build contexts. Reusing a plan-app OAuth client shares its branding, allowed callbacks and secret-rotation lifecycle; add callbacks rather than replacing existing ones, and coordinate rotation across both applications.

Execution environment operations are administrator-only, CSRF-protected, versioned requests; the provisioner independently validates user IDs, action names, numeric limits and Docker ownership labels. It publishes status through a separate volume that the gateway mounts read-only. This requires one gateway and one provisioner writer. An interrupted restart is not automatically replayed. The provisioner and its short-lived privileged quota helper are trusted host administration components; user runners do not gain these privileges.

Persistent storage limits use XFS project quotas over each user's workspace and runtime-data directories, with unique project IDs and Docker volume subpath isolation. Source volumes survive migration. Memory, CPU and process count are cgroup limits; a file-size limit is a process rlimit. These are separate constraints: the persistent quota does not account for tmpfs memory, Docker logs, or IPC socket storage. Quotas do not reserve physical host space. Back up the image filesystem and the project-ID registry consistently before storage maintenance.

The local onboarding listener exists only until onboarding is completed. Compose publishes it on the Docker host's loopback interface, and Caddy does not proxy it. Its boundary is a random one-time code printed to the gateway log, which only Docker-privileged operators can read. The listener also checks that the Host header is a loopback name, which stops DNS rebinding. It uses its own SameSite=Strict cookie and CSRF token, rejects cross-origin posts, and rate-limits code attempts. Other containers on the gateway's `edge` network can reach the port but still need the code. The listener can promote one pending Google account to the first administrator, using the same preconditions as the CLI bootstrap, and can set the workspace root. Both changes are audited with actor `local_installer`.

Host-directory workspaces bind-mount `<root>/<name>` from the Docker host. The root is chosen only by the local installer. Web administrators can choose only a validated directory name under it, never a path. An unprivileged helper running as `DEV_UID` from the runner image creates each directory exclusively, so existing host directories are never assigned. The helper checks before every start, restart and recreation that the directory is a real directory, not a symlink, owned by `DEV_UID`. The root may not be or lie inside another runner's reserved host workspace, such as an administrator environment migrated from an older installation's shared runner. The gateway rejects such a root lexically when it is saved. The provisioner's helper makes the authoritative check by comparing the device and resolved path of the root and each reserved workspace in `/proc/self/mountinfo`, so symlinks or bind aliases cannot hide an overlap. It repeats this check before every start, restart and recreation. Therefore no runner can see another account's host workspace. Docker resolves bind sources when a container starts, including automatic restarts after a daemon restart. Only someone with write access to the root on the host could replace a directory between the check and a start; no runner has that access. Host directories have no storage quota.

`scripts/migrate-primary-runner.sh` moves an older installation's shared runner account to a dedicated runner. It is an operator command run on the Docker host with gateway and provisioner stopped, and refuses ambiguous or non-Google accounts. It removes the legacy password hash, keeps credential versions, and deletes nothing. The migrated environment keeps its old host directory. If that directory contains other sensitive host data (for example an IPC key directory or Google credential copies placed inside it), that runner can read it; keep such data outside workspaces.
