# Security policy

This service intentionally exposes arbitrary shell execution and destructive workspace operations after OAuth authorization. Treat every access token and administrator Google account as high-value credentials.

Report vulnerabilities privately to the repository owner. Do not include real access tokens, password hashes, workspace contents, or audit logs in a public issue.

The supported boundary is the current main branch. Docker daemon compromise, upstream container image or package-registry compromise, and host-kernel/container-runtime escapes are outside the application threat model.

Optional Remote - SSH runs in a separate per-account development container behind a shared OpenSSH entry on external TCP 2222. Entry accounts authenticate a registered public key and may forward only to their account's exact SSH alias on 2222, without session channels. A second public-key check authenticates the `workspace` login. MCP and development share project files, but have separate HOME, PID and network namespaces. No account container gets a host Docker socket, another account's mounts, or gateway/control-plane data.

MCP runners use read-only roots, dropped capabilities, no-new-privileges and a private temporary HOME. They have no sudo or SSH authentication mount. A read-only mode-000 mount masks the legacy developer HOME inside the shared workspace. Development containers permit passwordless sudo, ordinary Docker capabilities and a writable root filesystem, without privileged mode or host namespace access. Their private HOME persists in an account-UUID volume; they receive no MCP IPC key, socket or runtime-data mount. The migration snapshots directly installed development packages without importing that image into MCP. Subsequent ordinary recreation restores recorded packages and persistent HOME, but resets the writable image layer.

Development's seccomp profile additionally permits nested namespace and mount operations for local shell sandboxes. It grants no additional capabilities; mounting in the parent namespace still fails without CAP_SYS_ADMIN. On AppArmor hosts, the dedicated `dev-mcp-workspace` profile allows inner sandbox setup and denies access to sensitive proc/sys paths. Selecting this profile removes Docker's conflicting proc overmounts so an inner PID namespace can mount proc. The policy loader persists this profile on the host for reboot and runs briefly with MAC_ADMIN, no account data or Docker socket, and no other added capability. MCP runners retain their original confinement. Host kernel/container-runtime escapes remain outside the application boundary.

Only Git identity, regular-file HTTPS credentials and gh hosts authentication are exported from the development HOME. Git aliases, helpers, includes, gh aliases/extensions, startup files, SSH private keys and AI credentials are excluded. MCP mounts the export read-only and uses a private gh copy to allow CLI configuration migrations. Developer login changes and logout are exported every five seconds. MCP instructions prohibit invoking, installing, authenticating or delegating to other coding agents, including through alternate execution paths. Arbitrary shell and language runtimes remain available: this isolation blocks access to developer programs and credentials, not deliberate installation using newly supplied credentials or deliberate disclosure through shared project files.

The trusted provisioner validates ownership and private SSH networks and maintains root-owned, read-only authorized-key mounts and persistent host keys. Key changes close SSH sessions; disabled accounts stop both account containers during reconciliation. Authorization leases renew independently of Docker work and expire after 30 seconds. Arbitrary-shell users with sudo control their own development daemon and programs, so these supervisors protect ordinary authentication behavior but cannot prevent deliberate sharing by the account owner. Preserve authentication volumes in backups.

Personal development lifecycle requests are authenticated, CSRF-protected, versioned and scoped to their owner. They affect only the development container; administrator lifecycle requests affect both MCP and development, with the latest applicable request taking precedence. Completed controls from the former MCP-only lifecycle are adopted without replaying them on development during upgrade. Storage copies stop both writers to prevent concurrent writes. Resource administration remains administrator-only. User-detail pages expose browser sessions, live MCP sessions and OAuth grants; grant revocation deletes only that user's matching access/refresh tokens and authorization codes. Role/status saves invalidate authentication only when values change, and actual changes also expire SSH registrations.

The separate provisioner is a trusted host control-plane service with Docker daemon access and a read-only account database mount. It has no network or HTTP endpoint, polls approved accounts, validates UUID and runner identity, and invokes a fixed creation helper. The gateway and all runners have no Docker access. Pending/disabled accounts are skipped; existing stopped containers are not restarted automatically. Approval withdrawal cannot cancel a Docker creation already in flight, but account authentication checks continue to block access.

Every approved account, administrators included, receives a dedicated runner container, workspace/data storage, a bridge network, and an authenticated IPC endpoint; there is no shared runner. The gateway chooses the runner from the authenticated account; clients cannot supply a runner identity. Every IPC call is HMAC-signed with the account's own key. Runners refuse to start without a key and reject unsigned requests, so redirecting one account's socket to another runner fails authentication. No runner mounts the shared parent IPC directory.

Projects are private to their owner's execution environment. Administrators can inspect users and project metadata; administrator privileges are trusted service-wide privileges. Do not promote untrusted users.

Disabling an account or revoking its credentials prevents subsequent authenticated requests and image retrieval. Account disablement also stops its containers on the next successful provisioner reconciliation; token revocation alone does not terminate already-dispatched commands. All containers still share the host kernel, and default resource limits do not prevent a user from consuming excessive host resources. Apply host/container resource limits for untrusted workloads.

The gateway must run as a single process when using the JSON stores; the in-process write queue does not coordinate multiple gateway replicas. Back up user records together with OAuth state so credential versions are not rolled back independently.

Accounts are created only by Google OIDC sign-in and require administrator approval. No account is seeded, and there is no password login, password registration or account linking. The first administrator is approved through the local onboarding, or with the gateway stopped through the CLI bootstrap. Google identities are bound by the verified `sub`, never matched or merged by email, and cannot be reassigned through the login flow.

Google sign-in uses state, nonce and PKCE; ID tokens must have a valid RS256 signature from Google's keys, accepted issuer, correct audience/authorized party, recent issuance, unexpired lifetime and verified email. Browser and MCP credentials are issued only for active accounts. Google access/refresh tokens are not persisted. Provider errors are not reflected or logged. Authentication URLs containing codes/transactions are omitted from Caddy access logs, and form pages use `Referrer-Policy: same-origin` to preserve native form Origin headers while suppressing cross-origin referrers (non-form pages use `no-referrer`); configure any upstream proxies consistently.

Google credentials are loaded only by the gateway at runtime. `scripts/import-google-secrets.mjs` copies the named files without reading their contents into logs or command arguments; `compose.google.yaml` mounts only the two files, never the whole plan-app directory. Preserve the mode-0700 parent directory of the read-only copies. Keep originals, copies and backups out of repositories/build contexts. Reusing a plan-app OAuth client shares its branding, allowed callbacks and secret-rotation lifecycle; add callbacks rather than replacing existing ones, and coordinate rotation across both applications.

Execution environment operations are administrator-only, CSRF-protected, versioned requests; the provisioner independently validates user IDs, action names, numeric limits and Docker ownership labels. It publishes status through a separate volume that the gateway mounts read-only. This requires one gateway and one provisioner writer. An interrupted restart is not automatically replayed. The provisioner and its short-lived privileged quota helper are trusted host administration components; user runners do not gain these privileges.

Persistent storage limits use XFS project quotas over each user's workspace and runtime-data directories, with unique project IDs and Docker volume subpath isolation. Source volumes survive migration. Memory, CPU and process count are cgroup limits; a file-size limit is a process rlimit. These are separate constraints: the persistent quota does not account for tmpfs memory, Docker logs, or IPC socket storage. Quotas do not reserve physical host space. Back up the image filesystem and the project-ID registry consistently before storage maintenance.

The local onboarding listener exists only until onboarding is completed. Compose publishes it on the Docker host's loopback interface, and Caddy does not proxy it. Its boundary is a random one-time code printed to the gateway log, which only Docker-privileged operators can read. The listener also checks that the Host header is a loopback name, which stops DNS rebinding. It uses its own SameSite=Strict cookie and CSRF token, rejects cross-origin posts, and rate-limits code attempts. Other containers on the gateway's `edge` network can reach the port but still need the code. The listener can promote one pending Google account to the first administrator, using the same preconditions as the CLI bootstrap, and can set the workspace root. Both changes are audited with actor `local_installer`.

Host-directory workspaces bind-mount `<root>/<name>` from the Docker host. The root is chosen only by the local installer. Web administrators can choose only a validated directory name under it, never a path. An unprivileged helper running as `DEV_UID` from the runner image creates each directory exclusively, so existing host directories are never assigned. The helper checks before every start, restart and recreation that the directory is a real directory, not a symlink, owned by `DEV_UID`. The root may not be or lie inside another runner's reserved host workspace, such as an administrator environment migrated from an older installation's shared runner. The gateway rejects such a root lexically when it is saved. The provisioner's helper makes the authoritative check by comparing the device and resolved path of the root and each reserved workspace in `/proc/self/mountinfo`, so symlinks or bind aliases cannot hide an overlap. It repeats this check before every start, restart and recreation. Therefore no runner can see another account's host workspace. Docker resolves bind sources when a container starts, including automatic restarts after a daemon restart. Only someone with write access to the root on the host could replace a directory between the check and a start; no runner has that access. Host directories have no storage quota.

`scripts/migrate-primary-runner.sh` moves an older installation's shared runner account to a dedicated runner. It is an operator command run on the Docker host with gateway and provisioner stopped, and refuses ambiguous or non-Google accounts. It removes the legacy password hash, keeps credential versions, and deletes nothing. The migrated environment keeps its old host directory, with the same access as before.

Apps run arbitrary user code and are served at `<name>.<PREVIEW_DOMAIN>`, never on the console's origin, where a page could read console pages and act with a visiting administrator's session. `PREVIEW_DOMAIN` is either the console host itself, which puts apps at `<name>.<console host>`, or a separate domain. The gateway refuses a parent of the console host, where an app could take the console's own name.

Apps under the console host are same-site with it:

- **Cookies:** every console cookie is `__Host-`, so app pages can neither read nor overwrite them. That holds only over HTTPS, which this layout therefore requires.
- **Requests:** SameSite does not separate apps from the console. Every console state change still needs its CSRF token and an exact `Origin` match, and no GET request changes state.
- **Parent-domain cookies:** an app can set cookies for a parent domain. Those reach the console, which ignores them, and other sites under that domain, which should use `__Host-` cookies and check `Origin` too. Oversized cookies can make the console reject that browser's requests until they expire or are cleared.

A separate registrable domain avoids the last point.

- **Separate listener:** the app listener has no console routes.
- **Runner tunnels:** reaching a runner uses its signed IPC socket. A timestamped request opens a byte stream, and a replayed or stale request is refused. Redirecting one account's socket to another runner fails that runner's HMAC check.
- **Private apps:** the console grants a single-use, 60-second code bound to the app and viewer. The app host turns it into its own HMAC-signed, host-only cookie, bound to the app and to the viewer's credential version. The proxy removes this cookie from forwarded requests and drops upstream attempts to set it.
- **Certificates:** on-demand TLS issues certificates only for hosts the gateway confirms as existing apps.
- **Public apps:** public links are reachable by anyone and can be disabled service-wide by administrators.
- **Limits:** an app's own server is responsible for its security, and the gateway applies no rate limiting to app traffic.
